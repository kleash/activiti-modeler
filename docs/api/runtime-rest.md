# Runtime REST API

The REST API of the modeler's runtime, in two parts that are separate libraries ([ADR 0007](../adr/0007-runtime-rest-split-and-security.md)):

| Library | What | Where it runs |
|---|---|---|
| `activiti-runtime-rest-core` | Definitions, instances, tasks, events, jobs, the engine report. | Any host Spring Boot application that embeds Activiti 9.0.0 (see the [integration guide](../integration-guide.md#runtime-rest-core-in-a-host-application)) and the modeler server |
| `activiti-runtime-rest-dev` | Validate, deploy, run scenarios, evaluate decisions, the project files on disk. | Only when `activiti.rest.dev.enabled=true`. The modeler server turns it on; a production host must not |

The machine-readable description is generated by springdoc from the controllers and written by a test of each module, so it cannot drift from the code:

| File | Content |
|---|---|
| [`openapi-core.json`](openapi-core.json) | The core API (written by `activiti-runtime-rest-core`'s `OpenApiExportTest`) |
| [`openapi-dev.json`](openapi-dev.json) | The dev API (`activiti-runtime-rest-dev`) |
| [`openapi-server.json`](openapi-server.json) | Everything the modeler server publishes: core, dev and the server's own `GET /api/health` and `/api/dev/mail` |

The TypeScript client `modeler/packages/runtime-client` is generated from these files and a unit test fails when they and the client differ. The paths below are relative to the base path (`activiti.rest.base-path`, default `/api`).

## Conventions

**Acting user.** The acting user is always the authenticated principal. No request body or parameter names a user: a body with a `user` or `userId` member is rejected with 400 (unknown members are refused in every request body). Starting an instance, claiming, releasing, assigning to oneself and completing all run as the principal, through `ProcessRuntime` and `TaskRuntime`, so the engine's visibility rules apply: a user who is not a candidate of a task gets 404 for it, not 403.

**Access levels.** Every endpoint needs one of three levels. A higher level includes the lower ones (`admin` includes `operate` includes `read`). The authorities behind them are properties (`activiti.rest.roles.read`, `.operate`, `.admin`; lists of granted-authority strings; defaults `ROLE_ACTIVITI_USER`, `ROLE_ACTIVITI_USER`, `ROLE_ACTIVITI_ADMIN`). No authentication gives 401, an authenticated principal without the authority gives 403. The library contributes **no** `SecurityFilterChain`: the host authenticates, the library only checks authorities.

| Level | Meaning |
|---|---|
| `read` | Look: engine report, deployments, definitions, instances, history, variables, tasks, jobs |
| `operate` | Act as the user: start instances, claim / release / complete tasks, hand a task over, send messages and signals, manage instances, variables and jobs |
| `admin` | Reassign any task, delete the history of an ended instance, and every dev endpoint |

**Errors.** Errors are `application/problem+json` (RFC 9457) with `type`, `title`, `status`, `detail`, `instance` and two extension members: `engineException` (class of the exception the engine threw) and `rootCause` (class and message of the innermost cause, when different). The dev endpoints add `problems[]` (see below).

| Status | When |
|---|---|
| 400 | Malformed JSON, an unknown member in the body, a missing or invalid parameter, an invalid variable name or value |
| 401 | Not authenticated (written by the host's security, not by the library) |
| 403 | Authenticated without the authority the endpoint needs |
| 404 | The object does not exist, or the principal may not see it (tasks, instances) |
| 409 | The runtime's rules refuse it: task already claimed, instance ended or suspended, another scenario run in progress, optimistic locking |
| 413 | A workspace file or a dev request larger than the configured limit |
| 422 | The engine rejects the content: a model that does not deploy, a job that fails when executed, a dev request whose project has errors |
| 500 | Anything else; the stack trace is in the server log, not in the answer |

Limitation: errors that Spring MVC raises before it chooses a handler (405 for a wrong method, 415, an unknown path) are answered by the host's error handling. The modeler server sets `spring.mvc.problemdetails.enabled=true` so they are `problem+json` as well; a host that wants that sets the same property. The library cannot do it for the host.

**Lists** take `page` (from 0) and `size` (default 20, at most 200; `activiti.rest.default-page-size`, `max-page-size`) and answer `{ items, page, size, total }`.

**Absent members.** The engine's JSON mapper omits `null` members, so a member that is `null` is absent. The OpenAPI description marks the members that are always there as `required`; all others are optional.

**Variables** are JSON values. Strings, numbers and booleans are the process variable types of the same name, objects and arrays are JSON variables. A variable that holds an expression (`${...}`) is refused (400).

## Core endpoints

| Method and path | Level | Purpose |
|---|---|---|
| `GET /engine` | read | Activiti, Spring Boot and Java versions, history level and whether history is stored, async executor configured and active, the DMN engine, the `Connector` bean names, the Spring bean names an expression can use, the script engines, the base path |
| `GET /deployments` | read | Deployments (`nameLike`, `page`, `size`) |
| `GET /deployments/{id}` | read | One deployment |
| `GET /deployments/{id}/resources` | read | Resource names as stored, with their kind (`bpmn`, `dmn`, `extensions`, `image`, `other`) |
| `GET /deployments/{id}/resource?name=` | read | The text of one resource |
| `GET /process-definitions` | read | Definitions (`key`, `nameLike`, `latest`, `deploymentId`, `suspended`, `includeCounts`). Running and ended instance counts with `includeCounts=true` |
| `GET /process-definitions/{idOrKey}` | read | One definition, by id or by key (its latest version) |
| `GET /process-definitions/{idOrKey}/xml` | read | The BPMN XML as stored |
| `GET /process-definitions/{idOrKey}/extensions` | read | The entry of this process key in the deployment's `*-extensions.json` |
| `GET /process-definitions/{idOrKey}/decisions` | read | The DMN decisions deployed next to the process: table or expression, hit policy, inputs, outputs, rule ids, required decisions |
| `POST /process-definitions/{idOrKey}/suspend`, `/activate` | operate | Suspend or activate a definition |
| `POST /process-instances` | operate | Start through `ProcessRuntime`. Body `{ processKey \| processDefinitionId \| messageName, businessKey?, name?, variables? }` |
| `GET /process-instances` | read | Instances, running and ended (`state` = `all`, `running`, `active`, `suspended`, `finished`, `completed`, `cancelled`; `definitionKey`, `definitionId`, `businessKey`, `startedBy`, `parentId`) |
| `GET /process-instances/{id}` | read | State, definition, business key, starter, times, end reason, active activity ids, tasks, jobs, timers, dead-letter jobs, child instances, variables |
| `GET /process-instances/{id}/path` | read | The path: activities in order (with start, end, duration, kind) and the sequence flows taken. `sequenceFlowsSource` is `recorded` when the flows were recorded while the instance ran, `inferred` when they are derived from the model and the activities visited |
| `GET /process-instances/{id}/variables` | read | Variables with type; of an ended instance too (history) |
| `GET /process-instances/{id}/variables/history` | read | Every change of every variable, in order |
| `PUT /process-instances/{id}/variables` | operate | Set variables on a running instance. Body `{ variables }` |
| `DELETE /process-instances/{id}/variables?name=` | operate | Remove variables (repeat `name`) |
| `POST /process-instances/{id}/suspend`, `/activate` | operate | Suspend or activate |
| `DELETE /process-instances/{id}` | operate | Cancel a running instance (`reason`). `purgeHistory=true` deletes the history of an ended instance and needs **admin** |
| `GET /tasks` | read | Tasks (`processInstanceId`, `assignee`, `candidateUser`, `candidateGroup`, `unassigned`, `nameLike`, `taskDefinitionKey`; `mine=true` lists what `TaskRuntime` shows the principal; `candidates`, `variables` add the candidates and the task variables) |
| `GET /tasks/{id}` | read | One task, with candidates |
| `POST /tasks/{id}/claim`, `/release` | operate | As the principal |
| `POST /tasks/{id}/assign` | operate | Body `{ assignee }`. The assignee of a task hands it over (`TaskRuntime`); an **admin** reassigns any task (`TaskAdminRuntime`) |
| `POST /tasks/{id}/complete` | operate | Body `{ variables? }`, local to the task; they reach the process only through the output mapping |
| `POST /messages` | operate | `{ name, correlationKey?, variables? }` through `ProcessRuntime.receive`: starts a process with a matching message start event, or correlates (exactly one subscription) |
| `POST /signals` | operate | `{ name, variables? }`: broadcast to every waiting instance |
| `POST /executions/{id}/trigger` | operate | Continue an execution that waits at a receive task |
| `GET /jobs` | read | Jobs (`kind` = `JOB` executable, `TIMER`, `SUSPENDED`, `DEADLETTER`; `processInstanceId`, `withException`) |
| `GET /jobs/{id}` | read | A job in whichever table it is, with the stack trace of its last failure |
| `POST /jobs/{id}/execute` | operate | Execute an executable job now |
| `POST /jobs/{id}/retries` | operate | Body `{ retries }` |
| `POST /timers/{id}/fire` | operate | Fire a timer job now: `moveTimerToExecutableJob`, then execute. A timer of a repeating schedule plans its next occurrence as usual |
| `POST /deadletter/{id}/retry` | operate | `moveDeadLetterJobToExecutableJob`; `{ retries?, execute? }` runs it at once |

Engine services (not the runtimes) answer reads of history, jobs, timers, dead letters, children and ended instances, because `ProcessRuntime` shows an instance only to its starter and participants. The mutations that the runtimes offer (start, claim, release, assign, complete, message, signal) always go through them.

### Startup check

The library refuses to start unless the engine stores full history: `spring.activiti.history-level=full` and `spring.activiti.db-history-used=true`. The path of an instance, the variable history and ended instances all come from history. The failure analyzer prints the two properties to set. Without them the engine's defaults are history `NONE` and no history tables.

## Dev endpoints (`activiti.rest.dev.enabled=true`)

Every dev endpoint needs the **admin** level. They deploy models, which run code of the model's author on the server (JUEL, scripts, delegates), and they read and write files: remote code execution by design. The module logs a WARN at startup while they are on. They are not registered at all without the property (the paths answer 404).

| Method and path | Purpose |
|---|---|
| `POST /dev/validate` | Body `{ files: [{ path, content }] }`. Runs, in this order: the BPMN XSD, `RepositoryService.validateProcess`, a trial deployment into a **scratch engine** (a private in-memory engine, history off, executor off, closed afterwards, so it never touches the real data; it also catches failures that only appear on deployment), a dry load of the extensions JSON, and a parse of the DMN. Answers `{ valid, asyncExecutorActive, checked, problems[] }`. A problem is `{ path, elementId?, key, severity (error \| warning \| info), message, source (xsd \| engine-validate \| trial-deploy \| extensions \| dmn \| request), line?, column? }`. When this server's async executor is off the engine warns about every asynchronous element (`activiti-flow-element-async-not-available`...); those warnings say so in their message and are `warning`s, because the executor is on in the modeler server |
| `POST /dev/deployments` | Same body (plus `name?`). Validates, then deploys the files as **one deployment** with the names given. 201 `{ deploymentId, name, resources, definitions, decisions, problems }`. A project with errors is refused with 422 and `problems[]` |
| `DELETE /dev/deployments/{id}` | Delete a deployment with its instances, jobs and history (`cascade`, default `true`) |
| `POST /dev/scenarios/run` | Body `{ files, scenario }` (the scenario as JSON or as text, [format](../user-guide/scenarios.md)). Deploys the files, runs the scenario with the scenario runner in `EXECUTOR` mode and removes everything. Answers `{ passed, report, rendered, durationMillis }`; the report lists every step with its result. See "Scenario run isolation" |
| `POST /dev/decisions/evaluate` | Body `{ dmn \| deploymentId, decisionRef?, inputs }`. Evaluates a decision with the configured DMN engine: `{ decisionId, matched, rows, matchedRules, engine, decisions[] }` (every decision on the way, required decisions first) |
| `GET /dev/workspace` | Listing of the workspace root (`recursive`) |
| `GET /dev/workspace/{path}` | A directory (listing) or the text of a file |
| `PUT /dev/workspace/{path}` | Create or replace a file with the request body; parent folders are created. 201 when new, 204 when replaced. The write is atomic (temporary file, then move) |
| `DELETE /dev/workspace/{path}` | Delete a file, or a folder (empty, or `recursive=true`) |

### Workspace safety

The workspace is the folder `modeler.workspace.dir` (the server's `--workspace`). Without it the endpoints answer 404. Every path goes through these checks before anything is touched:

- no `..` or `.` segment, no hidden segment (starting with `.`), no backslash, no colon, no control character, no empty segment, no segment longer than 255 characters: 400;
- the resolved path stays inside the real path of the root, and no symbolic link on the way leads out of it: 400;
- only file names ending in an allowed suffix (default `.bpmn20.xml`, `.bpmn`, `.dmn`, `.json`, `.properties`, `.md`, `.txt`, `.svg`, `.png`; `modeler.workspace.allowed-suffixes`) can be read, written or deleted: 403;
- files larger than `modeler.workspace.max-file-size` (default 10 MB) are refused: 413;
- a missing file or folder: 404; writing to a folder or deleting a folder that is not empty without `recursive=true`: 409.

### Scenario run isolation

A scenario needs everything of the running server: its connectors (the recording wrapper is put around them), delegates, Spring beans, mail server, async executor. So the run happens **on the live engine**, not in a copy, in `EXECUTOR` mode (the job driver waits for the async executor, and also handles failed retry timers and optimistic-locking failures; see [scenarios](../user-guide/scenarios.md)). The files are deployed as a deployment of their own and removed, with everything the run created, when the run ends.

What is isolated, and what is not:

- **Runs are serialized.** A second run waits up to `activiti.rest.dev.scenario-lock-timeout` (30 s), then answers 409. The engine clock and the runner's recorders are global, so two runs at once would corrupt each other.
- **Instances of the run only.** Everything the runner queries and asserts is scoped to the instance tree of the scenario.
- **Not isolated:**
  - the runner deletes **every** process instance that appeared during the run, including one that somebody else started in that time;
  - a scenario with a `clock` or `advanceClock` moves the engine clock of the whole JVM for the run, so timers of other instances look due, and the clock is reset afterwards;
  - while the run lasts, the definitions of its files are the latest versions of their keys (a call activity of another project resolves to them), and the message and signal start events of the files are live;
  - the users a scenario defines exist in the server's user store for the run, with random passwords nobody knows.
- **Therefore** run scenarios on the modeler server (a developer's machine, where nothing else matters), never against a shared engine. This is one more reason the dev endpoints are opt-in.

A scenario run in a scratch engine would be isolated but could not call the server's own connectors, which is most of what a scenario of a real project does; that is why the live engine was chosen.

## Using the API

With the modeler server (`java -jar activiti-modeler-server.jar`, user `modeler` / `modeler`):

```bash
# what is running
curl -u modeler:modeler http://127.0.0.1:8080/api/engine

# deploy a project and start an instance
curl -u modeler:modeler -H 'Content-Type: application/json' \
  -d '{"files":[{"path":"processes/order.bpmn20.xml","content":"<definitions ...>"}]}' \
  http://127.0.0.1:8080/api/dev/deployments
curl -u modeler:modeler -H 'Content-Type: application/json' \
  -d '{"processKey":"order","variables":{"amount":5000}}' \
  http://127.0.0.1:8080/api/process-instances

# the tasks of the user, claim and complete
curl -u alice:alice 'http://127.0.0.1:8080/api/tasks?mine=true'
curl -u alice:alice -X POST http://127.0.0.1:8080/api/tasks/<id>/claim
curl -u alice:alice -H 'Content-Type: application/json' -d '{"variables":{"approved":true}}' \
  -X POST http://127.0.0.1:8080/api/tasks/<id>/complete
```

From TypeScript: [`@activiti-modeler/runtime-client`](../../modeler/packages/runtime-client/src/client.ts) (typed, one method per operation; Basic, bearer and cookie-with-CSRF authentication).

```ts
const client = new RuntimeClient({ baseUrl: 'http://127.0.0.1:8080', auth: basicAuth('modeler', 'modeler') });
const instance = await client.startProcessInstance({ processKey: 'order', variables: { amount: 5000 } });
const path = await client.getProcessInstancePath(instance.id);
```
