# Verification index

Every row of the [feature matrix](FEATURE_MATRIX.md), with the named tests that prove it and, for a row that is not fully supported, what is missing. The matrix gives the status; this page gives the evidence.

`DocsConsistencyTest` (`java/verification-harness`) fails when this page and the matrix disagree on a row or a status, when a `supported` row names no proof, when a `partly supported` row does not say what is missing, and when a scenario or a `model-expect.json` entry cited here does not exist. `scripts/verify-all.sh` runs the Java, Vitest and Playwright tests and the corpus builds named here; CI also runs the smoke scripts of the distribution rows (section K).

## 1. The three proof layers

Every §A row is judged on three layers. A row can be `supported` only with (b) and (c).

| Layer | What it is | Where it runs |
|---|---|---|
| **(a) Seed** | A hand-written project (`corpus/<id>/seed/processes`) with hand-written oracles: `corpus/<id>/scenarios/*.scenario.json`, `model-expect.json`, `coverage-exemptions.json`. Proves what **Activiti 9.0.0** does, independent of the modeler. | `CorpusVerificationTest` › `<id> [seed]` › auto-deploy and programmatic › one check per scenario / `decisions[]` entry, "model-expect.json", "path coverage", "DMN cross-check". |
| **(b) Generated** | The **same oracles** run against the project the modeler exported: `corpus/<id>/build.ts` drives the real modeler in Chromium through `window.__modelerTestApi` (the property accessors and commands the panel uses) and writes `java/verification-harness/target/corpus/<id>`. Two checks guard the build: Playwright `corpus.spec.ts` "`<id>`: models the seed, exports it and equals the seed semantically" (a difference to the seed fails unless the build declares it as intended, with a reason; six builds declare one) and the harness run itself. Every corpus project except N01 has a build (26). Seven of them (C01, C02, C04, C08, C11, C16, C20-loan) are also built through the real UI (`modeler/e2e/support/uiModeler.ts`: menus, palette, create menu, context pad, replace menu, properties panel, DRD, decision table cells), exported with File > Export project as zip into `target/corpus-ui/<id>` and run with the same oracles. | `CorpusVerificationTest` › `<id> [generated]` and `<id> [ui]`. They need `npm run corpus:build` first; `scripts/verify-all.sh` runs both (sections 10 and 11) and fails when a build has no output or the harness did not run it. |
| **(c) Modeler / UI** | Vitest on the accessors, behaviours, serializer, lint, project model; Playwright on the real panel and shell (types into the panel and asserts the exported XML / JSON). | `npm test`, `npm run e2e`. |

Abbreviations used in the tables:

- `C05/timer-starts "…"` is the scenario in `corpus/C05-timers/scenarios/timer-starts.scenario.json` whose `name` starts with the quoted text; the harness check is `timer-starts.scenario.json: <name>`. `C01`…`C22` map to the folders `corpus/C01-user-tasks` … `corpus/C22-camunda-import` (`C17-kie` is `C17-dmn-drd-kie`).
- `ME C05 timerStarts.startCron` is the entry `processes.timerStarts.elements.startCron` of `corpus/C05-timers/model-expect.json` (checked against the `BpmnModel` the engine parsed).
- `PW file "title"` is a Playwright test in `modeler/e2e/<file>.spec.ts`; panel tests live in `modeler/e2e/properties/` and are titled `<§B group>: <what>` (several are generated in loops by `properties/support.ts`: `typeCase`, `pickCase`, `checkCase`). A trailing `…` shortens the title.
- `UT file "title"` is a Vitest test (for example `accessors.test` = `packages/bpmn-js-activiti/src/modules/accessors/accessors.test.ts`, whose "property accessors: one case per accessor" runs one case per accessor key and checks the XML / JSON written, the value read back after a re-import, and undo / redo).
- `JT Class#method` is a JUnit test under `java/`.

## 2. Criteria for the Status column

The Status column of the matrix tables (§A, §E, §F, §G, §K) follows these rules; §B, §C, §D, §H and §J have no status and are described here only.

1. **`supported` (§A rows)** needs all of: (b) at least one named engine-level assertion on a **modeler-generated** project for **every** variant and property the row lists (hand-written seeds alone never qualify); (c) the panel / UI test for every user-facing property (a Playwright panel test or, for an element without properties, the reachability walk `ui-reachability.test` and its placement rules); and, when the row has an Extensions-JSON column other than "-", the mapping panel test as well. A row whose generated proof comes from another project qualifies when the assertion is named and covers the variant.
2. **`supported` (§E, §F, §G, §K rows):** a named test per behaviour in the row: an engine-level assertion where the row has engine behaviour, a Playwright test where it has a user interface, a smoke script for an artifact.
3. **`partly supported`** means part of the row is built and proven, and the row says which variant, layer or artifact is missing.
4. **`not supported`** means the feature is not built.

## 14. Known limitations

What the proof does not cover, and what the modeler does not do. The rows above give the details.

- **Not built:** diagram diff (U21), dark theme (U22), a native macOS wrapper (U23), a form editor (U24), headless rendering (U32) and the embeddable starter (K8, proposed in ADR 0009).
- **Translations (U29):** only the shell and the run workbench go through `t()`; the properties panel, the Problems panel, the decision tester, the DMN editor and the texts of bpmn-js and dmn-js do not. Only English ships.
- **Desktop bundles and releases (K4, K7):** CI builds and smoke-tests the Linux x64 bundle. The macOS and Windows bundles and the push of the Docker image to GHCR are tested only by the release workflow, on the runner of each system.
- **Databases:** every test runs on H2. Other databases and clustering are not tested (ADR 0002).
- **Not proven on a generated model:** the `stringValue` / `expression` attribute forms of a field injection (T2: the seed has them, the modeler writes the element form), and the skip expression of a service task (no scenario at all).
- **Lint rules without an engine pin:** L15 (process not executable, connector task without a name), L17 and L34 (unique message start names and process keys in a project), L27 (malformed JUEL), and some of the rules from the engine findings (section 9). No test asserts the switched-off bpmnlint rules or the downgrades of the tuning table.
- **Collaborations:** an annotation outside every pool stays in the collaboration, where Activiti does not read it and warns (`DI_INVALID_REFERENCE`); the lint does not report it (A1).
- **Weak oracles:** cron timers are checked as a 30-minute window, fired through `fireTimer` or the clock in one JVM time zone (C05/cron-timer). The start event's form key, the process documentation and legacy form properties are checked in the parsed model only, because no engine behaviour reads them.
- **The generated-equals-seed check** (`modeler/packages/activiti-project/src/semantic-diff.ts`) ignores default attribute values, an `xsi:type` the editor adds on timer and loop expressions, the generated ids of event definitions, `incoming` / `outgoing` and the layout. The engine ignores these as well, but no test proves it for each; the scenarios cover only what they observe.
- **Browsers:** Playwright and the corpus builds run in Chromium only; `ui-reachability.test` runs in jsdom. The local-folder storage is tested against the origin-private file system behind a stubbed folder picker (U3). Shortcuts are tested with Ctrl on Linux; the Cmd bindings have a unit test only (U28). Closing the status window with the frame's close button needs a display and is not tested (K3).
- **This page:** `DocsConsistencyTest` checks that the cited scenarios and `model-expect.json` entries exist, not that an assertion is sufficient, and it does not check the Playwright and Vitest citations.

## 15. How to re-run the proof

```bash
# layers (a) and (b): build the generated projects, then run the harness over the seeds and the generated output
cd modeler && npm run corpus:build            # writes java/verification-harness/target/corpus/<id> for every corpus/*/build.ts
cd .. && scripts/verify-models.sh corpus        # the seeds; the generated folder: scripts/verify-models.sh java/verification-harness/target/corpus
mvn -B -f java/pom.xml -pl activiti-scenario-runner,verification-harness -am verify   # CorpusVerificationTest: seeds and generated
# layer (c)
cd modeler && npm test && npm run e2e && npm run lint:corpus
```

`scripts/verify-all.sh` runs all of it in order.
